# Exercise 001 coding contd.

## 1. Start the Scheduler
- Start the FreeRTOS scheduler after creating the tasks:

```c
/* Start the FreeRTOS scheduler */
vTaskStartScheduler();

/* If control of the program reaches here, the launch of the
 * scheduler has failed due to insufficient heap memory */
```

- `vTaskStartScheduler()` normally never returns.
- If it *does* return, the scheduler could not start because there wasn't enough FreeRTOS heap memory to create the Idle task (or the Timer task, if enabled) — this is the only reason the function can fail.
- Internally, the scheduler start-up path itself calls `xTaskCreate()` to create the Idle task, which — like any other task — uses dynamic (`malloc`-based) allocation from the FreeRTOS heap. Tracing into `vTaskStartScheduler()` shows the exact comment in the kernel source: this line is reached "only if the kernel could not be started, because there was not enough FreeRTOS heap to create the idle task or the timer task."
- So the available heap must be large enough for the application's own tasks **plus** these kernel-created tasks.

## 2. Implement the Task Handlers
- Implement each task handler as an **infinite loop** — a task handler must never return.
- The exercise passes a message string to each handler through its `void *` parameter.
- Cast the parameter to `char *` and print it:

```c
static void task1_handler(void *parameters)
{
    while (1)
    {
        printf("%s\n", (char *)parameters);
    }
}

static void task2_handler(void *parameters)
{
    while (1)
    {
        printf("%s\n", (char *)parameters);
    }
}
```
> **Fix:** both handlers must be declared `static void ...`, not `static ...` with no return type — a task handler function must return `void`, matching the `TaskFunction_t` signature FreeRTOS expects. Missing the `void` here won't match the prototypes and will cause build errors/warnings.

- Include the standard I/O header for `printf()`:

```c
#include <stdio.h>
```

## 3. Print via SWO / ITM (not UART)
> **Correction:** this project does **not** print over a UART COM port. The lecture explicitly routes `printf()` output over the **SWO pin**, using the ARM Cortex-M4's **ITM** (Instrumentation Trace Macrocell) unit — an optional, application-driven trace source built for printf-style debugging.

- Hardware used in this exercise: an **STM32 Discovery board** with an **STM32F407VG** microcontroller, based on the **ARM Cortex-M4** processor.
- Message path: `printf()` → ITM unit of the Cortex-M4 → **SWO pin** (part of the SWD debug interface) → **ST-Link** circuitry on the board → **USB** → PC.
- **Important limitation:** the ITM/SWO mechanism described here only works on **ARM Cortex-M3, M4, and M7** cores. It is **not available on ARM Cortex-M0/M0+** cores, since those don't include an ITM unit.

### 3.1 Retarget `printf()` to ITM
1. Copy the `ITM_SendChar()` code snippet provided in the lecture's resource section.
2. Open `syscalls.c` in the project and paste the snippet in, right after the existing header includes. The function is named `ITM_SendChar()` — `printf()` ultimately calls it to push characters into the ITM's registers.
3. In `syscalls.c`, find the low-level `_write()` system call (the function `printf()` calls underneath, at the C-library level). Comment out its existing body and instead call `ITM_SendChar()` from it, passing each character along.
4. Add `#include <stdio.h>` wherever `printf()` is used (see Section 2).

- Typical shape of this retargeting (the exact snippet is provided in the course resources — this illustrates the pattern):

```c
/* in syscalls.c */
int _write(int file, char *ptr, int len)
{
    for (int i = 0; i < len; i++)
    {
        ITM_SendChar((uint32_t)*ptr++);
    }
    return len;
}
```

> **Background (not from the lecture):** to actually *see* this output, the debugger's SWV (Serial Wire Viewer) / ITM data console needs to be opened and configured with the correct core clock frequency once you start a debug session — the SWO trace won't display anything on its own just because the code is retargeted correctly.

### 3.2 Fixing a Possible `vApplicationIdleHook` Build Error
- If the build fails complaining about an undefined/unimplemented `vApplicationIdleHook` (a hook function the kernel's Idle task calls when idle-hook support is enabled):
  - Open `FreeRTOSConfig.h`.
  - Set `configUSE_IDLE_HOOK` to `0`.

```c
// FreeRTOSConfig.h
#define configUSE_IDLE_HOOK   0
```

- Rebuild — this removes the requirement to provide a `vApplicationIdleHook()` implementation. *(Idle task and timer task are covered in more detail in a later lecture.)*

## Result
- The scheduler is started after the two tasks are created.
- Both task handlers loop forever, printing their message via `printf()`.
- Output is routed over **SWO/ITM**, not UART — reaching the PC via the board's ST-Link circuitry over USB.
- After setting `configUSE_IDLE_HOOK` to `0`, the project builds successfully.
- Testing this on real hardware is covered in the next lecture.
