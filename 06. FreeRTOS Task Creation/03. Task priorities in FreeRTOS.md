# Task priorities in FreeRTOS

## 1. What Is Task Priority?
- A priority value must be supplied whenever a FreeRTOS task is created (the `uxPriority` parameter of `xTaskCreate()`).
- Priority only becomes meaningful in a **multitasking** system — one where two or more tasks exist and compete for the CPU.
- Most exercises in this course assume a **single-processor** system, where one or more tasks compete for that one CPU. To resolve this CPU contention and achieve multitasking, different tasks are assigned different priorities.
- The priority value helps the scheduler decide which task should run first on the processor.
- **Lower the priority value → lower the task's priority → lower the urgency.**
  - Numerically higher priority = more urgent/important task.
  - Numerically lower priority = less urgent task.

## 2. Priority Range
- In FreeRTOS, each task can be assigned a priority value from `0` to `configMAX_PRIORITIES - 1`.
- `configMAX_PRIORITIES` is a configuration item defined in `FreeRTOSConfig.h`.
- There is no strict guideline or standard value for `configMAX_PRIORITIES` — it is entirely application-specific; you decide it based on your application's needs.

```c
// FreeRTOSConfig.h
#define configMAX_PRIORITIES   5   // valid task priorities: 0, 1, 2, 3, 4
```

- If unsure what value to use, `5` is a reasonable default — giving five distinct priority levels (`0`–`4`).
- Increase this number only if you have a solid reason to do so.

## 3. Performance Considerations
- Assigning too many different task priority values (i.e., allowing many tasks to run with varying priorities) can lead to **RAM overconsumption** and reduced system performance.
- Reasoning behind this:
  1. More distinct priorities → more tasks actively contending → more **context switches** happening in the system.
  2. Every context switch carries its own overhead in both **time** and **space**:
     - **Time overhead** → increases CPU overhead (more cycles spent switching instead of running application code).
     - **Space overhead** → each context switch consumes stack bytes (to save/restore task context), so more context switches mean more cumulative stack memory consumption.
- Net effect: too many priority levels → more context switching → higher CPU overhead + higher RAM usage → degraded overall system performance.
- *(How context switching works internally, and exactly how it consumes RAM, is covered in a later lecture.)*

## 4. Return Value of `xTaskCreate()`
- `xTaskCreate()` returns a `BaseType_t` value indicating success or failure.
- If the task was created successfully, it returns `pdPASS`.
- If task creation fails, the failure is **always** related to insufficient memory — since `xTaskCreate()` allocates the task's TCB and stack dynamically (from the heap), it can only fail if the kernel is unable to allocate that memory.
- Always check the return value in application code:

```c
TaskHandle_t xTask1Handle = NULL;
BaseType_t xReturned;

xReturned = xTaskCreate(
                 vTask1Handler,      // Task function
                 "Task-1",           // Task name (for debugging)
                 configMINIMAL_STACK_SIZE,  // Stack depth (in words)
                 NULL,                // Parameters
                 1,                   // Priority
                 &xTask1Handle        // Task handle (output)
             );

if (xReturned == pdPASS)
{
    // Task created successfully — kernel was able to allocate required memory
}
else
{
    // Task creation failed — insufficient heap memory
}
```

## Key Points
- Task priority values range from `0` to `configMAX_PRIORITIES - 1`, with `0` being the lowest priority.
- Lower numeric value → lower priority → lower urgency.
- `configMAX_PRIORITIES` is application-specific; `5` is a reasonable default when unsure.
- Too many distinct priority levels → more context switches → higher CPU time overhead and higher RAM (stack) usage → potentially worse overall performance.
- `xTaskCreate()` returns `pdPASS` on success; any failure is due to insufficient heap memory for the dynamically allocated task.
